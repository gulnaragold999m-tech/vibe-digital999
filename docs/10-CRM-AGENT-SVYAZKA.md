# Связка: панель заявок как CRM для агента

Как закрыть пункт 4 ТЗ («Активные продажи и CRM») на своей панели вместо
amoCRM или Bitrix24. Разобрано на том, что уже построено, а не на планах.

---

## Что уже есть

Панель `Дизайн Студия Гранат/crm-panel` — это фактически CRM, просто её так
не называли:

| Требование ТЗ | Чем закрыто сейчас |
|---|---|
| Воронка продаж | этапы: Новое ТЗ → В работе → На согласовании → Оплачено → Готово / Отказ |
| Карточка сделки | `orders` — клиент, ТЗ, параметры, файлы, деньги, заметка |
| Контроль этапов | таблица `history` — кто когда куда переехал |
| Сроки | поле `deadline`, дашборд с просрочками |
| Деньги | `price`, `prepay`, `paid`, `payment_status` |
| Аналитика | раздел «Статистика»: по дням, месяцам, папкам |

То есть три четверти CRM уже стоит. Не хватает только того, что делает
её **активной**.

---

## Чего не хватает

1. **Бот не пишет в базу.** Заявка уходит владельцу в личку и исчезает.
2. **Нет истории переписки.** Агенту нечего анализировать перед дожимом.
3. **Нет отсчёта времени с последнего касания.** Не понять, кто «завис».
4. **Нет книги продаж.** Агенту нечем крыть возражения.

---

## Схема связки

```
Клиент ──▶ Джарвис (Telegram)
              │
              ├──▶ orders.db  ◀── панель заявок (ты смотришь и правишь)
              │        ▲
              │        │
              └────────┴──── followup.py (по расписанию Amvera Cron)
                                 │
                                 └──▶ LLM + книга продаж ──▶ сообщение клиенту
```

База `orders.db` на диске `/data` — единственная точка правды. И бот,
и панель, и дожимающий скрипт работают с ней.

---

## Шаг 1. Бот пишет в базу

Правка в `Джарвис Гранат/jarvis_bot.py`. Заявка создаётся **на первом же
вопросе**, а не после подтверждения:

- начал диалог → `db.add_order(...)` со статусом **«Черновик»**
- отвечает на вопросы → `db.update_order(...)` дописывает параметры
- прислал фото → `db.add_attachment(...)`
- подтвердил ТЗ → статус меняется на **«Новое ТЗ»**
- бросил на середине → так и остаётся «Черновик»

Черновики — самое ценное для продаж. Видно, на каком вопросе люди уходят,
и есть кому написать «вы не закончили заявку, помочь?».

В базе появляется статус `Черновик` перед `Новое ТЗ`.

---

## Шаг 2. История переписки

Новая таблица в `db.py`:

```sql
CREATE TABLE messages (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    order_id   INTEGER NOT NULL,
    direction  TEXT NOT NULL,   -- 'in' от клиента / 'out' от нас
    author     TEXT,            -- 'клиент' / 'бот' / 'владелец'
    text       TEXT,
    sent_at    TEXT NOT NULL
);
```

Бот пишет сюда каждое сообщение в обе стороны. Это и есть та «долгосрочная
память», о которой говорится в `08-AGENT-ARCHITECTURE.md` — без неё агент
дожимает вслепую.

---

## Шаг 3. Отсчёт времени и стадия дожима

Три поля в `orders`:

| Поле | Смысл |
|---|---|
| `last_contact_at` | когда последний раз был контакт в любую сторону |
| `followup_stage` | сколько дожимов уже отправлено: 0, 1, 2, 3 |
| `next_followup_at` | когда отправлять следующий |

По ТЗ интервалы **24 / 48 / 72 часа**. После третьего дожима — стоп,
заявка помечается «остыла» и ждёт ручного решения. Четвёртого касания нет:
дальше это уже назойливость, а не продажа.

---

## Шаг 4. Книга продаж

Обычный файл `crm-panel/sales_book.md`. Векторная база (Pinecone, Qdrant
из твоего документа) на твоих объёмах не нужна — пока заявок сотни,
а не сотни тысяч, книга просто целиком кладётся в промпт.

Структура:

```markdown
## Возражение: «Дорого»
Что стоит за ним: не видит разницы с типографией за углом.
Ответ: развернуть в ценность — 6 часов работы, контроль каждого оттиска,
        визитка, которую не выбрасывают.
Чего не делать: не сбрасывать цену первым.

## Возражение: «Я подумаю»
...
```

Заполняешь ты — это твой опыт, не мой. Начни с пяти самых частых.

---

## Шаг 5. Скрипт дожима

Файл `crm-panel/followup.py`, запускается **раз в час** через
Amvera → **Cron Jobs** (раздел в панели у тебя уже есть).

Что делает:

1. Берёт заявки, где `next_followup_at <= сейчас` и статус в списке
   «зависших»: Черновик, Новое ТЗ, На согласовании.
2. Собирает контекст: карточку заявки + всю переписку из `messages`
   + книгу продаж.
3. Просит LLM написать **одно** сообщение под конкретного клиента и стадию.
4. Кладёт его в очередь на отправку.
5. Двигает `followup_stage` и `next_followup_at`.

---

## Шаг 6. Мгновенная реакция

По ТЗ — обработка новой заявки за 2 минуты. Реализуется без всякого
расписания, прямо в боте: как только клиент подтвердил ТЗ, бот сразу

- отвечает клиенту, что заявка принята и когда с ним свяжутся,
- шлёт тебе уведомление,
- если сумма считается по прайсу — сразу отправляет предоплату к оплате
  и QR-код СБП.

Это уже почти работает, надо только добавить запись в базу.

---

## Где притормозить

**Первые дожимы — с твоего одобрения.** Скрипт не отправляет сразу,
а кладёт черновик в панель, в раздел «На отправку». Ты читаешь, правишь,
жмёшь «Отправить». Когда наберётся 20–30 удачных — включаем автоотправку.
Иначе первый же кривой текст уедет живому клиенту от имени студии.

**Telegram не любит массовых рассылок.** Дожим по одному клиенту с интервалом
в сутки — нормально. Рассылка по всей базе разом — риск блокировки бота.

**Согласие на обработку данных** у тебя в боте уже берётся кнопкой — это
основание и для дожимающих сообщений. Но в каждом должна быть возможность
отписаться одной фразой, и на «не пишите мне» дожим прекращается навсегда.

## Порядок внедрения

| Очередь | Что | Зачем сначала |
|---|---|---|
| 1 | Бот пишет в базу (шаг 1) | без этого не работает ничего |
| 2 | История переписки (шаг 2) | нужна для любого анализа |
| 3 | Мгновенная реакция (шаг 6) | быстрый эффект, ничего не ломает |
| 4 | Поля отсчёта (шаг 3) | подготовка к дожиму |
| 5 | Книга продаж (шаг 4) | заполняешь ты, не блокирует код |
| 6 | Скрипт дожима с ручным подтверждением (шаг 5) | самое рискованное — в конец |

Шаги 1–3 — это один вечер работы. Остальное по мере накопления живых заявок:
дожимать пока некого, клиентов в базе нет.
